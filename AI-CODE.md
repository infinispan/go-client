# Coding Instructions

## Tech Stack
* **Go Version:** 1.25+ (see `go.mod`)
* **Build Tool:** `go build`, `go test`
* **Key Libraries:** `google.golang.org/protobuf`, `testcontainers-go`

## Project Architecture

* **`hotrod/`** — Public API. Client, RemoteCache, MultimapCache, TypedCache, NearCache, ContinuousQuery, SchemaManager, CacheAdmin, options, and marshallers. This is the package users import.
* **`internal/codec/`** — Hot Rod 4.1 wire protocol encoding/decoding: headers, varints, media types, time units, constants, and LP-bytes.
* **`internal/connection/`** — Connection pool, topology management, consistent hashing, and listener dispatch. Supports `Execute` (hash-routed) and `ExecuteOn` (server-targeted) dispatch.
* **`internal/operation/`** — Individual Hot Rod operations (Get, Put, Remove, Query, PutAll, GetAll, Multimap, Exec, etc.). Each operation implements the `Operation` interface; keyed operations also implement `KeyedOperation`.
* **`internal/auth/`** — SASL authentication mechanisms (SCRAM-SHA-256, PLAIN, EXTERNAL).
* **`internal/hash/`** — MurmurHash3 (Infinispan variant) and bloom filter implementation.
* **`internal/protostream/`** — WrappedMessage protobuf encoding/decoding compatible with Infinispan's ProtoStream format.
* **`internal/testproto/`** — Generated protobuf types for integration tests.
* **`test/`** — Integration tests (require Docker via testcontainers).
* **`examples/`** — Runnable example programs (e.g., `vector-search/`).
* **`documentation/`** — AsciiDoc user guide.

## Common Build Commands
* **Build all:** `go build ./...`
* **Run unit tests:** `go test -short ./...`
* **Run integration tests:** `go test -timeout 120s ./test/...`
* **Run a single test:** `go test -run TestName -v ./path/to/package/`
* **Vet:** `go vet ./...`

## Development Standards

### Code Style
* Follow standard `gofmt` formatting (tabs, no trailing whitespace).
* Use the functional options pattern for configurable constructors (see `hotrod/options.go`).
* Exported types and functions go in `hotrod/`. Internal implementation details go in `internal/`.
* Keep the `internal/` boundary strict — nothing outside the module should import `internal/` packages (except `test/` for integration tests).

### Naming Conventions
* Operations: `XxxOp` structs in `internal/operation/` implementing the `Operation` interface. Related operations may share a file (e.g., all multimap ops in `multimap.go`).
* Response types: `XxxResponse` structs co-located with their operation.
* Options: `XxxOption` function types with `WithXxx` constructor functions.
* Cache types: `RemoteCache` for key-value, `MultimapCache` for multimap, `TypedCache[K,V]` for typed, `NearCache` for near-cached. Each is a lightweight wrapper over `Client`.
* Constants: `OpXxx` for opcodes, `StatusXxx` for status codes, `MediaIDXxx` for media type IDs.

### Wire Protocol
* All new operations must implement the `Operation` interface in `internal/operation/operation.go`.
* Operations that route by key must also implement `KeyedOperation` (adds `KeyBytes() []byte`).
* Use `codec.WriteLPBytes` / `codec.ReadLPBytes` for length-prefixed byte fields.
* Use `codec.WriteVInt` / `codec.ReadVInt` for variable-length integers.
* Use `codec.EncodeTimeUnits` for lifespan/maxIdle encoding in put-like operations.
* Opcodes and status codes are defined in `internal/codec/constants.go`.
* For bulk operations (PutAll/GetAll), entries are sharded by consistent hash and dispatched in parallel via `pool.ExecuteOn`. Operations that are not keyed use `pool.Execute` which falls back to the round-robin balancer.
* Multimap operations append a `U1(supportsDuplicates)` byte after the operation-specific body. Use the shared helpers in `internal/operation/multimap.go`.

### Protobuf / ProtoStream
* Use `internal/protostream/` for encoding/decoding WrappedMessage envelopes.
* Do not use reflection-based protobuf libraries at runtime for wire encoding — hand-encode protobuf fields for performance.
* Use `WrapMessage` (field 16 + 17) for type-name-based wrapping, `WrapByTypeID` (field 19 + 17) for type-ID-based wrapping.

### Error Handling
* Return errors using `fmt.Errorf` with `%w` for wrapping.
* Do not panic in library code.
* Check `context.Context` cancellation where appropriate.

### Concurrency
* Guard shared state with `sync.Mutex` (see `lru.go`, `pool.go`).
* Use `sync/atomic` for counters accessed from multiple goroutines.
* Goroutines started by the library must be tied to a `done` channel or context for clean shutdown.
* For parallel dispatch (e.g., bulk operations), use `sync.WaitGroup` with error channels rather than adding external dependencies like `errgroup`.

### Commit Logs
* Commit messages start with `[#00000] Summary` where `00000` is the issue number.

### PRs
* Use the pull request template when creating PRs.
* Do not include "generated by" attribution lines.

### Git Branches
* Branches should be named `issueid/issue_summary` and use `origin/main` as the upstream.
* Only version branches (e.g., `main`) should be pushed to `origin`. Feature branches must be pushed to a personal fork.

### Public API Design
* Cache types are lightweight wrappers: they hold a `*Client` reference and a cache name, and delegate to `pool.Execute`.
* Use the functional options pattern (`WithXxx` functions) for configurable constructors and method parameters.
* When variadic values conflict with variadic options, provide a `XxxWithOptions` variant that takes explicit slices (see `MultimapCache.Put` vs `PutWithOptions`).
* Administration operations (create/remove cache) use the `Exec` opcode with server task names (`@@cache@create`, `@@cache@getorcreate`, `@@cache@remove`).
* Schema management uses the `___protobuf_metadata` internal cache (see `hotrod/schemas.go`).
